# arXiv Digest

Сервис по расписанию собирает препринты arXiv по темам (наборам поисковых запросов), суммаризирует их локальной LLM (OpenAI-совместимый API), собирает PDF-дайджест на русском и рассылает его по email. По кнопке переводит выбранную статью в docx. Полное ТЗ — `arxiv-digest-prompt.md`.

## Архитектура

- `backend/app/core` — конфиг (`pydantic-settings`), логирование (`structlog`), БД, безопасность, ошибки, middleware.
- `backend/app/models` — модели SQLAlchemy 2.0, общие для API и Celery.
- `backend/app/api` — тонкие роутеры FastAPI; `backend/app/services` — бизнес-логика; `backend/app/tasks` — тонкие Celery-задачи.
- `backend/app/services/translation` — перевод статьи в docx: `model` (блоки документа), `html_source` и `pdf_source` (разбор), `translator` (LLM), `omml` (формулы), `docx_writer` (сборка), `service` (оркестрация и БД).
- `frontend/src` — админка (React + Vite + Mantine): `api/` (axios-клиент, типы, вызовы), `pages/`, `components/`, `lib/`; nginx отдаёт статику и проксирует `/api` на backend.
- Compose: `postgres`, `rabbitmq`, `backend`, `worker` (очереди `default,mail`), `worker-llm` (очередь `llm`), `beat`, `frontend`; профиль `debug` — `flower`, `mailpit`.

## Соглашения

- Секреты — только из переменных окружения; в БД, логах и ответах API их нет. Новый секрет нужно добавить в `Settings.secret_values()`, а имя поля — в `SENSITIVE_KEYS` (`core/logging.py`).
- Все даты в БД — `timestamptz` в UTC; в таймзону из `TZ` переводятся только при отображении.
- FastAPI работает с БД через `asyncpg` (`get_session`), Celery и Alembic — через `psycopg` (`get_sync_sessionmaker`).
- Ошибки API — `{"detail": ..., "code": ...}`; бизнес-ошибки бросаются как `AppError` и наследники (`core/errors.py`).
- Логи — через `get_logger(__name__)`, события в snake_case, данные — именованными полями.
- Схема меняется только миграциями Alembic.

## Принятые решения

- **Enum-колонки хранятся строками** (`native_enum=False`), а не нативными типами PG: новое значение не требует `ALTER TYPE`.
- **Статус `cancelled` у `task_runs`** добавлен сверх ТЗ: отменённый вручную запуск не должен выглядеть как `failed`.
- **`task_runs.params`** (JSONB) добавлено сверх ТЗ: входные параметры запуска (период, `digest_id`, `force`).
- **`papers.full_text`** хранится в БД (TEXT, deferred), отдельных txt-файлов нет.
- **Один дайджест профиля на период** (`UNIQUE(profile_id, period_start, period_end)`): повторная сборка обновляет ту же запись.
- **`summaries.paper_id` уникален**: пересуммаризация заменяет резюме.
- **`updated_at` обновляется на стороне Python** (`onupdate=utcnow`), чтобы async-сессии не требовался повторный SELECT.
- **arXiv API вызывается по https** (`https://export.arxiv.org/api/query`): адрес из ТЗ с `http://` отвечает редиректом 301.
- **Пауза `ARXIV_REQUEST_DELAY_SECONDS`** выдерживается между любыми запросами к arXiv — и к API, и при скачивании PDF.
- **Статус пайплайна выводится из шагов** (`services/runs.py::_sync_parent`): ошибка или отмена шага переводит оставшиеся шаги в `skipped`, отдельной финализирующей задачи нет.
- **Ретраи на уровне задачи** — только для `RetryableError` и ошибок соединения с БД (до 3 раз, 60/120/240 с); запуск на это время возвращается в `queued`, причина — в `error`.
- **Повторный `collect`** дообрабатывает статьи, оставшиеся в `new` / `downloaded`, и те `failed`, у которых текст так и не был извлечён.
- **Список литературы** отрезается по первому заголовку References / Bibliography после первых 30% текста; приложения после него тоже отбрасываются.
- **Обновление сущностей — `PATCH`** с частичным телом (кроме singleton `PUT /smtp`).
- **Фильтр логов по уровню — «не ниже»**: `level=warning` возвращает warning, error и critical.
- **Ретраи LLM делает наш клиент** (`services/llm_client.py`, 3 попытки, 2/4 с), у SDK `max_retries=0`: так каждый ретрай и таймаут попадает в лог.
- **Недоступность LLM**: перед суммаризацией выполняется healthcheck; если модель недоступна, все выбранные статьи получают `failed`, запуск падает с `LLMUnavailableError`. Три ошибки соединения подряд посреди запуска прерывают его так же. Ошибка отдельной статьи (например, невалидный ответ) остальные не прерывает.
- **`summarize` берёт только `text_extracted`** (как в ТЗ). Статьи, упавшие на суммаризации, подбираются параметром запуска `retry_failed` или кнопкой «пересуммаризировать».
- **Конспекты map-шага пишутся по-русски**; если они не помещаются в `LLM_CONTEXT_CHARS`, перед reduce сжимаются группами (collapse).
- **Проверка ответа модели**: не пустой, без служебных фраз, не короче 200 символов, итоговое резюме — не меньше половины букв кириллицей. Блоки `<think>` и Markdown вырезаются.
- **Формулы печатаются обычным текстом**: промпты запрещают LaTeX, а `services/latex_text.py` переводит оставшийся код формул в текст и Юникод (`$\hat{\beta} \le 0.5$` → `β ≤ 0.5`). Преобразование применяется к ответу модели (`clean_response`) и ещё раз при сборке PDF — к названию статьи и резюме. Индексы и скобки разбираются только внутри `$...$`, `\(...\)`, `\[...\]`.
- **Проверка релевантности** (сверх ТЗ, `LLM_RELEVANCE_CHECK`): в начале `summarize` модель по названию и аннотации оценивает статью для каждой нашедшей её темы — `relevant` / `partial` / `irrelevant` (`services/relevance.py`, критерий — название и описание темы). Оценка и причина хранятся в `paper_topics.relevance` / `relevance_reason` и повторно не запрашиваются. Статья отбрасывается, только если по всем темам получено явное `irrelevant`: статус `irrelevant`, PDF и `full_text` удаляются, запись остаётся, чтобы сбор не скачивал её снова. Ответ не по формату оценкой не считается (статья остаётся), `partial` статью сохраняет.
- **Что проверка релевантности не трогает**: статьи, выбранные явно (`paper_ids`, кнопка «пересуммаризировать»), статьи без тем и без аннотации. Тема, для которой статья `irrelevant`, не печатает её в своём разделе дайджеста. Если отброшенную статью позже находит другая тема, `collect` скачивает её заново, и оценивается только новая связь.
- **Краткая аннотация** (`summaries.abstract_ru`, сверх ТЗ): один абзац из 4–6 предложений, пишется отдельным запросом (`purpose="abstract"`) по аннотации с arXiv, а если её нет — по первым 6000 символам текста статьи. Запрос идёт до map-reduce: если модель не справилась, статья получает `failed`, не потратив время на полный текст. Проверка ответа — как у итогового резюме; подпись «Аннотация:» и переводы строк из ответа убираются.
- **Аннотации для старых резюме**: параметр запуска `fill_abstracts` (только для `summarize`) дописывает `abstract_ru` статьям `summarized`, у которых его нет, не трогая резюме и статус; новые статьи в таком запуске не суммаризируются. В stats `summarized` — число дописанных аннотаций. Ошибка статьи оставляет её без аннотации.
- **Состав карточки дайджеста** (`DigestContent`: `abstract` / `full` / `summary`): по умолчанию из `DIGEST_CONTENT` (`full`), параметр запуска `digest_content` (для `full_pipeline` и `build_digest`) его переопределяет; расписания всегда берут значение из окружения. Состав последней сборки хранится в `digests.content`. В режиме `abstract` статья без `abstract_ru` печатается разделами резюме, чтобы карточка не осталась пустой. Подпись «Аннотация:» в PDF ставится, только когда под ней идут разделы.
- **`LLM_EXTRA_BODY`** (JSON) добавлен сверх ТЗ: дополнительные поля запроса, например отключение reasoning.
- **`GET /api/llm/health` всегда отвечает 200**, состояние — в поле `ok`.
- **В дайджест попадают статьи** со статусом `summarized` и `published_at` внутри периода. Темы идут по алфавиту; «первая тема» статьи — первая по этому порядку, в остальных разделах стоит ссылка на карточку.
- **Период в заголовке PDF**: целые сутки UTC показываются датой с пометкой «(UTC)», произвольный интервал — в таймзоне `TZ`. Даты статей и время формирования — в `TZ`.
- **PDF создаётся и для пустого дайджеста** (статус `empty`), чтобы его можно было разослать при `SEND_EMPTY_DIGEST=true`.
- **Имя файла** — `digest_YYYY-MM-DD.pdf` по дате периода в UTC; для периода в несколько дней — `digest_НАЧАЛО_КОНЕЦ.pdf`. Так файл называется на диске; во вложении письма, при скачивании и в поле `filename` API перед датой стоит название профиля: `digest_<профиль>_YYYY-MM-DD.pdf` (`services/files.py::digest_filename`). Имя с профилем вычисляется при отдаче, поэтому переименование профиля меняет его сразу и для старых дайджестов. В названии пробелы и запрещённые в именах файлов символы заменяются дефисом, кириллица остаётся, длина — до 50 символов.
- **Рассылка**: одно SMTP-соединение на запуск, после ошибки оно открывается заново; паузы между тремя попытками — 5 и 15 с. Если к серверу не удалось подключиться за все попытки для одного получателя, остальным сразу ставится `failed` без перебора.
- **Итог `send_digest`**: никому не доставлено → запуск `failed` (статистика сохраняется в `stats`); нет активных получателей, нет готового дайджеста или дайджест пуст при `SEND_EMPTY_DIGEST=false` → запуск `skipped` с причиной в `error`.
- **`POST /digests/{id}/resend`** по умолчанию шлёт всем заново (`force=true`); с `force=false` — только тем, кому не доставлено.
- **Удаление и очистка** (сверх ТЗ): `DELETE /{digests,papers,runs}/{id}` удаляет одну запись, `DELETE` на коллекцию — все записи под теми же фильтрами, что у списка (без фильтров — все), ответ `{"deleted": N}`. Вместе с записями удаляются PDF-файлы. Статьи и дайджесты нельзя удалять при активных запусках (409 `runs_active`); активный запуск удалить нельзя (409 `run_active`), очистка истории его пропускает. Удаление статьи убирает её из состава дайджестов, но уже собранный PDF не меняется.
- **`POST /smtp/test`** при ошибке отвечает 400 с кодом `smtp_error` или `smtp_not_configured`.
- **nginx резолвит `backend` через DNS Docker** при запросах (`resolver 127.0.0.11`), иначе после пересоздания backend прокси отдаёт 502.
- **Планировщик опирается на `next_fire_at`**: расписание срабатывает, когда `next_fire_at <= now` и последнее плановое время по cron больше `last_fired_at`. API при создании и изменении расписания ставит `next_fire_at` в будущее, поэтому новое расписание не запускается «задним числом». Каждое расписание обрабатывается в своей транзакции под `FOR UPDATE SKIP LOCKED`, отметка о срабатывании коммитится вместе с записью запуска.
- **Некорректное расписание в БД** (битый cron или таймзона) тик деактивирует и пишет ошибку в лог.
- **Защита от параллельного пайплайна**: `pg_advisory_xact_lock` сериализует проверку «есть ли у профиля `full_pipeline` в `queued`/`running`» и создание запуска; лишний запуск создаётся сразу со статусом `skipped` и причиной в `error`. Отдельные шаги (collect и т.д.) этой защитой не ограничены.
- **Зависшие запуски**: если у запуска и его шагов нет изменений и новых записей в `task_logs` дольше `PIPELINE_STALE_HOURS`, тик и запуск пайплайна помечают их `failed`. Иначе убитый воркер блокировал бы пайплайн навсегда.
- **Период запуска по расписанию** фиксируется в момент срабатывания: предыдущие сутки UTC.
- **Состояние LLM на дашборде кешируется на 30 секунд**; статус SMTP — проверка заполненности настроек, без подключения к серверу.
- **`task_logs` сбрасываются в БД фоновым потоком раз в секунду** (и сразу при 20 записях в буфере), чтобы просмотр логов в UI не отставал, пока задача молчит в ожидании LLM.
- **`GET /api/settings`** добавлен сверх ТЗ: несекретные параметры окружения для UI, в первую очередь таймзона отображения дат.
- **Frontend**: типы API описаны вручную в `src/api/types.ts`; даты форматируются в таймзоне сервиса (`useFormat`); ошибки запросов и мутаций показываются уведомлениями централизованно в `src/lib/queryClient.ts`; опрос (`refetchInterval`) работает и в неактивной вкладке.
- **Темы задаются поисковыми запросами** (`topics.queries`), а не ключевыми словами: каждый запрос — выражение arXiv API и выполняется отдельным обращением к arXiv. Вся работа с синтаксисом — в `services/arxiv_query.py` (токенизатор, `normalize_query`, `validate_query`, `build_search_query`).
- **Запросы тем пишутся по `abs:` / `ti:`, а не по `all:`**, и многозначные слова в них всегда связаны с контекстом предметной области: arXiv не различает регистр и приводит слова к основе (`ODD` находит «odd», `"autonomous train"` — «autonomous training»), поэтому формы числа отдельно не перечисляются. Принципы записаны в шапке `seed_topics.yaml`.
- **Нормализация запроса**: пробелы схлопываются; строка без префиксов полей и без заглавных операторов считается фразой и превращается в `all:"..."`. В БД хранится нормализованный вид.
- **Что считается ошибкой запроса**: несбалансированные скобки и кавычки, неизвестный префикс, пустые скобки и кавычки, оператор в начале, в конце или два подряд, префикс без значения, слово или фраза без префикса внутри выражения, длина больше 1000. `and` / `or` строчными и отсутствие оператора между условиями — предупреждения, сохранению не мешают. Позиции считаются с нуля по нормализованной строке.
- **Ошибка запроса в API** — 422 с элементом `{loc: ["body", "queries", <индекс>], msg, position, type: "invalid_query"}`; `position` добавляет обработчик ошибок только для этого типа.
- **`keywords` в API тем — deprecated**: если клиент прислал `keywords` без `queries`, они превращаются в `all:"..."` с WARNING в логе; в ответах поля нет.
- **`paper_topics.matched_keywords` оставлена** для старых записей и больше не заполняется; `matched_queries` накапливает нормализованные запросы, нашедшие статью, в том числе между запусками.
- **Лимит `ARXIV_MAX_RESULTS_PER_TOPIC` — на тему**: запросы идут по порядку, каждому достаётся остаток лимита по уникальным статьям; при исчерпании — WARNING, оставшиеся запросы помечаются в stats как пропущенные.
- **Статистика collect**: `topics[имя].queries` — словарь «нормализованный запрос → found / new / duplicates / errors (и error)». У темы `found` — уникальные статьи, `duplicates` — те из них, что уже были в БД.
- **Ошибки запросов при сборе**: невалидный запрос и постоянная ошибка arXiv по одному запросу пропускаются с ERROR и отметкой в stats; `ArxivUnavailableError` по-прежнему роняет шаг на ретрай.
- **Полный URL запроса к arXiv пишется на DEBUG** (`arxiv_request`), на INFO — запрос и счётчики (`arxiv_page`, `collect_query_started`).
- **В YAML и в теле preview категории называются `categories`**, в БД и CRUD тем — `arxiv_categories`.
- **Preview темы** выполняется в процессе API отдельным клиентом arXiv, по одной странице (до 100 статей) на запрос; одновременно один предпросмотр на процесс (`threading.Lock`), иначе 429 `preview_busy`. С паузами воркера `collect` он не координируется. Число уникальных статей считается по загруженным страницам, поэтому может быть нижней оценкой (`unique_is_lower_bound`).
- **Импорт тем**: файл — `multipart/form-data`, `mode` и `dry_run` — query-параметры. Весь файл проверяется до записи; при ошибках `dry_run` отдаёт их в отчёте (200), обычный импорт — 422 `import_invalid`. `replace` обновляет совпавшие по имени темы (id и связи сохраняются), добавляет новые и удаляет отсутствующие в файле.
- **Seed тем**: `python -m app.cli init` импортирует `SEED_TOPICS_PATH` в первый профиль, только пока таблица `topics` пуста; ошибка в файле пишется в лог и старту не мешает.
- **В PDF-дайджесте под названием раздела печатается `description` темы** (раньше — ключевые слова); сами запросы в PDF не выводятся.
- **Редактор темы**: проверка запросов на лету через `validate-query` (debounce 400 мс), перетаскивание — `@hello-pangea/dnd`; модальное окно открывается без transform-анимации, иначе перетаскиваемая строка смещается.
- **Категории arXiv в форме темы** — `TagsInput` с подсказками популярных категорий и свободным вводом.
- **Период ручного запуска** выбирается датами и трактуется как целые сутки UTC.
- **Перевод статьи** (сверх ТЗ): задача `translate` в очереди `llm`, запускается только `POST /papers/{id}/translate` — в расписаниях и `POST /runs` этот тип отклоняется (422). Таблица `translations`: один перевод на пару «статья — язык» (`UNIQUE(paper_id, language)`), повторный заменяет файл; пока перевод в `queued` / `running`, второй такой же — 409 `translation_active`. Файлы — `DATA_DIR/translations/<profile_id>/<arxiv_id>_<язык>.docx`.
- **Язык перевода** — код из списка `services/translation/languages.py` (ru, en, de, fr, es) либо название, введённое вручную; название языка из списка приводится к коду. Служебные слова документа («Аннотация.», «Рис.», «Список литературы») для языков из списка заданы в коде, для введённого вручную остаются английскими. Последний выбранный язык фронтенд хранит в `localStorage`.
- **Источник структуры статьи**: сначала HTML-версия arXiv (`arxiv.org/html/<id>v<версия>`, разметка LaTeXML), при её отсутствии, ошибке загрузки или почти пустом тексте — сохранённый PDF; источник записывается в `translations.source`. Запросы к arXiv (страница и каждый рисунок) идут через `ArxivClient.fetch` с той же паузой `ARXIV_REQUEST_DELAY_SECONDS`. Название и аннотация берутся из HTML (там формулы), авторы — всегда из метаданных arXiv.
- **Строчные формулы в тексте заменяются метками `<fN/>`**, сами формулы лежат в `Document.math`: модель переводит текст и обязана вернуть метки на месте. Формула, состоящая только из числа («95%»), остаётся текстом. Если после повтора метки потеряны, абзац переводится ещё раз с формулами обычным текстом.
- **Проверка перевода**: не пустой, метки формул совпадают с исходными, длина — от 35% оригинала до 4× + 200 символов, для русского — не меньше 30% букв кириллицей. Один повтор с указанием причины; ответ, оборванный лимитом токенов, приводит к делению фрагмента пополам. Абзац, который перевести не удалось, остаётся на языке оригинала (stats `untranslated`), перевод при этом не падает; недоступность модели прерывает запуск.
- **Что и как отправляется модели**: абзацы — по одному запросу (длинные делятся по предложениям на порции `LLM_TRANSLATE_CHUNK_CHARS`), короткие строки (заголовки, ячейки таблиц, выделенные начала абзацев) — пачками по 20 нумерованных строк, нераспознанные строки пачки допереводятся по одной. Числа, обозначения и аббревиатуры без слов не отправляются; листинги и список литературы не переводятся. Лимит ответа — `LLM_TRANSLATE_MAX_TOKENS`, а не `LLM_MAX_TOKENS`.
- **Формулы в docx — OMML** (`services/translation/omml.py`, свой конвертер MathML → OMML; LaTeX → MathML — `latex2mathml`). Большой оператор (сумма, интеграл) набирается как `m:nary` и забирает выражение до ближайшего знака отношения; без выражения — обычным знаком с пределами, иначе Word показал бы пустую рамку. Растягиваемые скобки — `m:d`.
- **Формулы из PDF**: выключная формула определяется по доле математических шрифтов в строке, её куски из соседних блоков объединяются, область вырезается картинкой (200 dpi), а LLM по извлечённому тексту восстанавливает LaTeX. В контейнер попадают набранная формула и вырезка оригинала под ней; если LaTeX дважды не разобрался — только вырезка. Строчные формулы в PDF остаются текстом.
- **Разбор PDF — эвристики** (`pdf_source.py`): название, авторы и аннотация берутся из метаданных, шапка статьи до первого раздела отбрасывается; абзац склеивается через границу колонки или страницы, если не кончается знаком конца предложения (рисунки, таблицы и сноски между частями не мешают); таблицы без вертикальных линий ищутся по линейкам под подписью «Table N», колонки — по промежуткам, пустым в 80% строк, а если колонки не нашлись, таблица остаётся картинкой.
- **Оформление docx — по образцу `Пример перевода.docx`**: A4, поля 2 / 1,5 / 2 / 2,5 см, Arial 11, отступ первой строки 284 twips; рисунок и формула — в таблицах-контейнерах без рамок (у формулы колонки 8831 + 808 twips, номер справа), идущие подряд формулы — строки одного контейнера; таблицы — с рамкой, шапка залита `D9E2F3` (без разметки шапки ею считается первая строка); список литературы — на языке оригинала.
- **Статус перевода и запуск**: отменённая задача завершается сигналом и статус перевода не обновляет, поэтому переводы в `queued` / `running`, чей запуск завершён или так и не появился за 5 минут, помечаются `failed` (`fail_orphaned`: при отмене запуска, в тике планировщика и перед новым переводом). Вместе со статьёй удаляются и файлы её переводов; `DELETE /translations` выполняющиеся переводы не трогает.
- **Отправка документов статьи** (сверх ТЗ): задача `send_paper` в очереди `mail`, запускается только `POST /papers/{id}/send` с телом `{recipient_ids, include_pdf, translation_ids}`; как и `translate`, в расписаниях и `POST /runs` отклоняется (`PAPER_TASKS` в `models/enums.py`). Каждому получателю — отдельное письмо с выбранными файлами; SMTP-настройки, повторы (3 попытки, 5 и 15 с) и правило «сервер недоступен — остальных не перебираем» те же, что у рассылки дайджеста (`services/paper_mailer.py` переиспользует `mailer.py`). Истории доставки в БД нет: итог по адресам — в `stats` запуска (`errors`: адрес → причина); никому не доставлено → запуск `failed`.
- **Получатели в окне отправки** — все из раздела «Получатели», включая неактивных: `is_active` относится только к рассылке дайджестов. Последние отмеченные получатели фронтенд хранит в `localStorage`. API до постановки в очередь проверяет наличие файлов (409 `no_pdf`, `no_translation_file`) и существование получателей и переводов (404); задача проверяет файлы ещё раз.
- **Профили** (сверх ТЗ): таблица `profiles`, колонка `profile_id` у `topics`, `recipients`, `schedules`, `task_runs`, `papers`, `digests`; переводы, резюме и связи принадлежат профилю своей статьи или дайджеста. Уникальность — в пределах профиля: `(profile_id, name)` у тем, `(profile_id, email)` у получателей, `(profile_id, arxiv_id)` у статей, `(profile_id, period_start, period_end)` у дайджестов. SMTP, LLM и администраторы общие. Миграция `0006` переносит прежние данные в профиль «Основной».
- **Профиль запроса** — заголовок `X-Profile-Id` (`ProfileDep` в `api/deps.py`); без заголовка — первый профиль по id, неизвестный id — 404 `profile_not_found`. Им ограничены списки, создание, очистка коллекций, дашборд и поиск по логам. Запросы к объекту по id профиль не проверяют: запуск, созданный от объекта (пересуммаризация, перевод, отправка, повторная рассылка), берёт профиль у самого объекта.
- **Профиль в задачах** — `task_runs.profile_id`: шаг читает его из своего запуска, в параметрах запуска профиля нет. Расписание запускает задачу в своём профиле. Защита от параллельного пайплайна и запрет удаления при активных запусках действуют в пределах профиля.
- **Удаление профиля** — только пустого (нет тем, получателей, расписаний, статей, дайджестов; иначе 409 `profile_not_empty`), не единственного (409 `last_profile`) и без активных запусков. Внешние ключи данных на профиль — `RESTRICT`, у `task_runs` — `CASCADE`: история запусков уходит вместе с профилем.
- **Статья, найденная двумя профилями**, — две независимые записи. При сборе PDF и извлечённый текст копируются у той же версии статьи из другого профиля (stats `text_reused`), при суммаризации так же копируется готовое резюме с аннотацией (stats `reused`), но не для явно выбранных статей (`paper_ids`, «пересуммаризировать»). Релевантность темам оценивается в каждом профиле отдельно.
- **Файлы профиля** лежат в подкаталоге с его id: `DATA_DIR/{papers,digests,translations}/<profile_id>/`. Файлы, созданные до появления профилей, остаются по прежним путям; при пересборке дайджеста или повторном переводе старый файл удаляется.
- **Тема письма с дайджестом** — `arXiv Digest - <профиль> - <дата рассылки>` (дата в таймзоне `TZ`); период дайджеста остаётся в заголовке тела письма.
- **Frontend и профили**: выбранный профиль хранится в `localStorage` и уходит заголовком из перехватчика axios (`api/client.ts`), ключи запросов профиль не содержат. При смене профиля кеш запросов (кроме общих: профили, пользователь, настройки, SMTP) очищается, а страница пересоздаётся по `key`.
- **Пароли — `bcrypt` напрямую** (без passlib), JWT — `PyJWT`, HS256, срок жизни 12 часов.
- **Healthcheck beat** проверяет только, что процесс жив: у beat нет команды ping.
- **Баннеры Celery отключены** (`celery --quiet`), чтобы в stdout шёл только JSON.
- **Frontend-контейнер** — `nginx-unprivileged`, слушает 80 без root.
- **Шрифты дайджеста** — PT Sans / PT Serif (OFL) в `backend/assets/fonts/`.
